    架构¶

    数据流¶

    EmptyLatentImage(512,512,1)
        │
   KSampler K0   denoise 1.0, seed 123456789
        │  LATENT ─────────────────────────┐
        ├──────────────► CLIPTextEncode K1 ─┐
        ├──────────────► CLIPTextEncode K2 ─┤
        ├──────────────► CLIPTextEncode K3 ─┤
        │                                   │
   CLIPTextEncode「全局动作指导」──► ConditioningCombine（每帧一个）
                                          │
                     KSampler K1/K2/K3  positive 走合并后的条件
                     denoise 0.35-0.4，与 K0 同 seed、同首帧 latent
                                          │
        N × LatentInterpolate（N = frames，8–60；每帧一个 ratio；同一对 latent 内不重复）
                                          │
        N × VAEDecode ◄── VAE
                                          │
        ImageBatchMulti(inputcount=N)
                ├──► SaveAnimatedPNG   → output/APNG/final/apng/
                ├──► SaveAnimatedWEBP  → output/APNG/final/webp/
                └──► VHS_VideoCombine  → output/APNG/final/gif/

    关键约束：

    1. 所有关键帧的 latent_image 都指向 K0 的 LATENT，不链式继承上一帧，否则颜色会累积漂移。 同时所有 KSampler 共用同一个 seed：seed 不同会带来不同噪声路径，插值时表现为色斑。
    2. 同一对 latent 上的 ratio 唯一。不同段（K0→K1 与 K1→K2）可以同值，样本对不同画面就不同；同一段里撞值才会被 Pillow 合并。
    3. 三个输出接同一个 batch，否则三种格式的帧序会不一致。

    帧数不是写死的¶

    --frames N（或剧情卡的 "frames": N）决定整条链的长度，--segs 之和必须等于 N：

    • 24 帧保留旧预设：3 拍 8/8/8、4 拍 6/7/6/5、5 拍 5/6/5/4/4；
    • 其它帧数按拍数平均分，余数给前几拍（30 帧 4 拍 → 8/8/7/7）；
    • ensure_frames() 会把 LatentInterpolate + VAEDecode 克隆到 N 个或删到 N 个， 再重建 ImageBatchMulti 的 image_1..image_N 与 widgets_values=[N]，并按 6 列重排画布位置。

    校验口径也改了：不再硬编码 24，而是要求「插值数 = 解码数 = batch 接线数」，且 batch 的计数值必须等于实际接线数。

    脚本分工¶

    脚本 输入 输出
    detect_env.py 磁盘上的 ComfyUI profiles/*.json
    doctor.py profile + 工作流 PASS/WARN/FAIL 清单
    emit_workflow.py base 工作流 + 剧情卡 K 拍工作流 JSON（含校验）
    emit_workflow.py --run 上述 + profile 提交 API、轮询、成品路径、自动校验
    check_anim.py 成品文件 帧数/时长/循环/差异/颜色漂移
    make_story.py 动作库 + 角色锁定句 剧情卡 JSON（frames/segs/fps/actions）
    make_curve.py 段数 N 个 ratio（N = sum(segs)）
    make_preview.py 成品 APNG 全局调色板 GIF + WebP 网页预览
    package.py 仓库目录 确定性 zip + SHA256

    曲线¶

    默认 linear：每段从 1.0 均匀降到 0.0，每帧步长恒定。

    段1: 1.0 0.857 0.714 0.571 0.429 0.286 0.143 0.0
段2: 0.996 0.861 ... 0.004        （段首与上一段末几乎相接）
段3: 0.992 0.853 ... 0.008

    ease 用 smootherstep，两端慢、中间快，单帧最大位移约为线性版的 1.9 倍； snap 是旧版幂曲线，前段几乎静止、末段猛冲，容易看成跳帧，只在对比时用。

    段与段之间留 0.004 的微差，避免 Pillow 把相邻的完全同值帧合并。

    UI → API¶

    --run 需要把 UI 工作流转成 API prompt。comfy_lib.ui_to_api 的做法：

    1. 用 /object_info/<type> 取节点的 required/optional 定义；
    2. 按 input_order 遍历，链接类型（MODEL/LATENT/...）走连线，其余取 widgets_values；
    3. 遇到 control_after_generate（如 KSampler 的 seed）多跳一格；
    4. 每个输入写成 [origin_node_id, origin_slot]。

    为什么不用脚本逐帧生成¶

    逐帧 img2img 需要每帧一次采样，N 帧就是 N 次采样；插值只需要 3–5 次采样 + N 次解码， 显存不变、耗时线性下降，而且中间帧由数学过渡，差异更均匀。 代价是没有真实运动轨迹，所以只适合微表演。

    实测口径（512²、8 步、24 帧）：逐帧重绘 40 s / 24 次采样，插值 15.5 s / 3 次采样； 逐帧方案的漂移会一路累积（0 → 38），插值是闭合的（峰值 16 → 末帧 1.5）。

    这条路线能控的：分镜（每拍提示词）、帧数、fps、拍内曲线、整段镜头（2D 平移/缩放/旋转 + 缓动）、 循环接缝。控不了的：真实 3D 视差、逐帧生成的新细节、复杂物理运动。 要那些效果就得回到逐帧或视频模型，代价是数量和漂移。

    为什么主产物是 APNG：逐帧无损、真彩 + alpha，不会被调色板量化；GIF 是兼容产物 （256 色，且相同帧会被合并、时长相加）。所以自检先看 APNG，GIF 只确认能播。
